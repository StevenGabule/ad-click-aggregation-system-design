Ang Misyon — intindihin muna bago magtayo

Bago tayo pumindot ng keyboard, linawin natin kung ano ba talaga ang problemang sinasagot ng sistemang ito — dahil bawat desisyon sa code ay babalik sa problemang ito.

Ang problema, sa isang pangungusap: kapag pinindot ng user ang isang ad, sisingilin ang advertiser — kaya ang bawat click ay dapat mabilang nang eksaktong isang beses: hindi zero (nawala sa network), hindi dalawa (na-retry at nadoble), at hindi isa kung bot pala ang "user".

Bakit mahirap ito? Dahil ang mga network ay at-least-once ang bigay na garantiya: walang mawawala, pero puwedeng dumating nang dalawang beses ang parehong mensahe. Nagta-timeout ang mga request, nagre-retry ang mga client, at may mga bot na nagpapanggap na tao. Ang madali, magbilang; ang mahirap, magbilang nang tama, nang mabilis, at nang mapapanindigan sa invoice.

Ang sentral na ideya: dalawang lane, iisang stream

Gusto ng dashboard ng numero sa loob ng ilang segundo, at okey lang na bahagyang mali. Gusto ng invoice ng numerong eksaktong tama, at okey lang maghintay hanggang bukas. Walang iisang sistema na mahusay sa pareho — kaya hindi tayo magpapanggap. Dalawang lane mula sa iisang Kinesis stream:

  • Fast lane — nagde-dedup sa pagpasok, nagbibilang sa 1-minutong windows na may watermark, at nagsisilbi ng tantiyang numero na tapat na naka-label na "exact": false.
  • Exact lane — ina-archive ang lahat ng raw event (kasama ang mga duplicate), tapos muling kino-compute ang billing gamit ang COUNT(DISTINCT cid) sa query time — kaya ligtas i-replay, at laging "exact": true.
Ang isang desisyong sandigan ng lahat

Ang click id (cid) ay ginagawa sa client side, bago ang unang hakbang na puwedeng ma-retry. Kapag nag-retry ang network, parehong cid ang ipapadala ulit — kaya makikilala ng downstream dedup na duplicate ito. Kung ang server ang gagawa ng panibagong id kada attempt, walang katalinuhan sa downstream ang makakapagligtas sa atin: ang retry at ang bagong click ay magiging magkamukha habambuhay.

02

Monorepo Skeleton

SP1 · Foundations

Itatayo natin ang balangkas ng monorepo: tatlong uri ng folder, iisang TypeScript config na minamana ng lahat, at pnpm workspaces na nag-uugnay sa kanila.

Ang monorepo ay isang git repository na naglalaman ng maraming maliliit na package sa halip na isang malaking app. Tatlong folder ang magkakaroon ng kahulugan dito:

  • packages/* — mga library: lohikang ini-import ng iba. Hindi sila "tumatakbo".
  • services/* — mga proseso: HTTP servers at stream consumers. Bawat isa'y may start script.
  • infra/* — mga setup script: gumagawa ng mga lokal na AWS resource.

Pansinin: ang typescript at vitest ay isang beses lang idinedeklara, dito sa ugat — mamanahin ito ng lahat ng package sa workspace, para hindi tayo mag-a-update ng dalawampung bersyon paglaon.

Ang allowBuilds: mula pnpm 10, hindi na basta-basta pinapatakbo ang mga install script ng mga dependency (isang security measure). Dito natin isinasaad kung alin ang pinagkakatiwalaan — kailangan itong patakbuhin ng Prisma (nagko-compile ng client) at ng DuckDB (may native binary). Idadagdag natin ang mga dependency na iyon sa mga susunod na hakbang, pero ideklara na natin ngayon para hindi tayo magulat.

Tandaan: ESM at ang dist/

ESM ang buong repo ("type": "module"). Dalawang kakaibang ugali nito na dapat mong tanggapin nang maaga: (1) ang mga import sa loob ng .ts file ay nagtatapos sa .js — hindi typo, ESM convention iyon, dahil ang tumatakbo talaga ay ang na-compile na dist/*.js; at (2) kapag ang services/query-api ay nag-import ng @app/db, ang binabasa ni Node ay packages/db/dist/index.js — kaya kung hindi mo pa nabu-build ang isang package, papalpak ang import dito. Iyan ang dahilan ng pnpm -r build sa mga susunod na checkpoint.

Ang mga package ay tutukoy sa isa't isa gamit ang "@app/db": "workspace:*" sa kanilang package.json — ibig sabihin, "i-link ang lokal na folder, hindi kukuha sa internet".

03

Ang Kontrata — event-schema at config

SP1 · Foundations

Ang unang code na isusulat natin ay hindi endpoint kundi kontrata: ang iisang opisyal na hugis ng isang click event, at ang typed na pagbabasa ng environment variables. Maliliit na package, pero sila ang dila na pagsasalitaan ng lahat ng susunod.

3.1 · @app/event-schema — ang hugis ng isang click

Kapag ang producer at ang consumer ay may kanya-kanyang ideya kung ano ang laman ng isang event, tahimik silang maghihiwalay ng landas balang araw. Kaya iisang package ang magmamay-ari ng hugis, at lahat — ingestion, aggregator, archiver, fraud scorer — ay mag-i-import dito.

Idagdag din ang pamilyar na tsconfig.json mula sa pattern sa Hakbang 02. Ganito na ang magiging hitsura ng bawat library package — pangalan at dependencies lang ang nagbabago.

Bakit TDD — at ganito ang ritmo

Sa repo na ito, test muna bago implementasyon, lagi. Hindi ito seremonya: ang test ang pumipilit sa iyong sabihin nang malinaw kung ano ang "tama" bago ka humarap sa "paano". Isusulat natin nang buo ang unang pares para makita mo ang ritmo; sa mga susunod na hakbang, sasabihin ko na lang kung ano ang tine-test at hahayaan kitang tumingin sa repo para sa kumpleto.

Patakbuhin — dapat pumalpak (wala pa ngang index.ts). Ngayon pa lang natin isusulat ang implementasyon, at pansinin kung gaano kaliit ang kailangan para paluntiin ang test:

05

Control Plane — Prisma, migration, at seed

SP1 · Foundations

Ang mga advertiser, campaign, ad, at API key ay control plane: mabagal magbago, ugnay-ugnay, at kailangang ma-query nang relational. Postgres + Prisma ang tamang kasangkapan dito — at dito lamang. Ang mga click mismo (ang data plane) ay hinding-hindi dadaan sa Postgres.

Tandaan: ang postinstall na iyan ay hindi palamuti

Ang Prisma client ay ginegenerate mula sa schema. Sa pamamagitan ng "postinstall": "prisma generate", kusang handa na ang client pagkatapos ng bawat pnpm install — walang lihim na dagdag na hakbang, at hindi kailangan ng koneksyon sa database para dito. (Ito rin ang dahilan kaya nasa allowBuilds natin ang Prisma mula pa Hakbang 02.)

Tatlong desisyon sa schema na ito
  • Ang signingSecret ay nasa Advertiser, hindi kada campaign o kada ad. Ang tenant boundary ng buong sistema ay ang advertiser ("hindi mababasa ng isang advertiser ang data ng iba") — kaya isang secret kada advertiser: parehong identifier ang ginagamit sa rotation at sa lookup.
  • Ang ApiKey.hashedKey ay sha256 lamang. Ang hilaw na key ay ipapakita nang isang beses sa paglikha at hinding-hindi itatago — kung matapon man ang database, walang mananakaw na kredensyal.
  • Walang foreign key ang Publisher papunta sa Ad. Ang pub_id ay naglalarawan kung saan nanggaling ang click, hindi kung ano ang pinindot — magkaibang dimensyon, kaya walang pilit na kadena.

Ang Prisma CLI ay kusang nagbabasa ng .env, pero ang Prisma client library (ang tumatakbo sa runtime at sa mga test) ay nagbabasa lamang ng tunay na process environment. Ang pag-prefix ng variable sa utos ang pinakasimpleng paraang maaasahan. Tatlong maliit na file. Ang client.ts ay iisang shared na instance ng PrismaClient; ang directory.ts ang query na magpapakain sa cache ng Hakbang 06:

5.2 · Ang idempotent na seed

Walang admin UI ang proyektong ito (sinadya — walang nangangailangan nito kundi tao na nagpapatakbo ng script), kaya isang seed script ang maglalagay ng demo data. Ang mahalagang katangian: upsert lahat, para ang muling pagpapatakbo ay hindi nagpaparami ng data.

Isang detalye na madaling makaligtaan: sa apiKey.upsert, ang update: { hashedKey } ay hindi blangko — bawat muling patakbo ng seed ay gumagawa ng panibagong API key at pinapalitan ang hash. Kung blangko iyon, ang ipi-print na bagong key ay hindi tutugma sa lumang hash sa database, at malulungkot ka sa Hakbang 08.

06

Ingestion — ang mga pinto ng click

SP2 · Ingestion APIs

Dalawang pinto ang papasukan ng bawat click: ang GET /click redirect (ang hot path — may taong naghihintay) at ang POST /v1/events/clicks batch upload (para sa mga mobile SDK na nag-ipon nang offline). Pareho silang magtatapos sa iisang validated na event sa ad-clicks-raw.

Ang pagkakasunod-sunod ng pagbuo (tatlong library muna, bago ang dalawang serbisyo): click-signature → directory-cache → kinesis-publisher → click-redirect → batch-ingest.

6.1 · @app/click-signature — ang pirma ng advertiser

Paano natin malalaman na ang isang click URL ay galing talaga sa ad server at hindi gawa-gawa? HMAC signature. Sa render time, pipirmahan ng ad server ang mga field ng click gamit ang lihim ng advertiser; sa ingestion, beberipikahin natin. Ang hindi makapagbigay ng tamang sig ay hindi papasok.

Bakit ganito ang beripikasyon
  • timingSafeEqual, hindi ===. Ang ordinaryong string compare ay humihinto sa unang maling byte — mula sa bilis ng sagot, kayang hulaan ng attacker ang signature nang paisa-isang byte. Ang constant-time compare ang pumipigil doon.
  • Ang length check bago ang compare ay hindi opsyonal: ang timingSafeEqual ay sumasabog kapag magkaiba ang haba, kaya kailangang harangin muna nang maayos.
  • Iisang canonicalize. Ang pagdidikit ng mga field gamit ang | ay kailangang eksaktong pareho sa pumipirma at sa bumeberipika — kaya iisang function, iisang package, walang kopya kung saan-saan.
  • Lowercase hex ang output — ligtas ilagay sa query string nang walang escaping.

Mga test (nasa src/index.test.ts): pumapasa ang pirmang parehong secret; bumabagsak kapag binago ang kahit isang field; bumabagsak sa ibang secret; at bumabagsak nang hindi sumasabog sa basurang signature na maling haba.

6.2 · @app/directory-cache — walang DB sa hot path

Ang redirect ay hindi puwedeng tumawag sa Postgres kada click. Kaya: isang in-memory na Map mula sa listActiveAdDirectory ng Hakbang 05, nire-refresh kada 30 segundo sa background.

Tatlong detalyeng sulit pansinin: (1) ang loadDirectory ay ipinapasa bilang parameter, hindi ini-import — kaya nate-test ang cache gamit ang pekeng loader, zero database; (2) ang lookup ay synchronous at puro memorya — ito mismo ang nag-aalis ng DB round-trip sa hot path; (3) ang timer.unref() ay nagsasabing "huwag mo akong hintayin" — hindi mabibitin ang proseso dahil sa refresh timer.

6.3 · @app/kinesis-publisher — isang lugar lang ng salting

Ganito ang publisher sa puntong ito (may idadagdag tayong maliit sa Hakbang 10):

Bakit may #0-7 sa partition key

Ang partition key ang nagpapasya kung aling shard ang pupuntahan ng record. Kung ad_id lang ito, ang isang viral na ad ay dadagsa lahat sa iisang shard — ang klasikong hot shard na problema. Ang random na salt na 0–7 ay nagkakalat ng isang ad sa hanggang 8 shards. Ang lohikang ito ay nakatira sa iisang package na ginagamit ng dalawang pinto — kaya magkapareho sila dahil sa konstruksyon, hindi dahil sa paalala sa dokumentasyon. Idinadagdag din dito ang receivedAt (kailan natin nakita) sa tabi ng ts (kailan talaga pinindot) — ang agwat ng dalawa ang "lateness" na haharapin natin sa Hakbang 07.

6.4 · services/click-redirect — ang hot path

Ito ang tanging code sa buong sistema na hinihintay ng tao. Ang mga serbisyo sa repo na ito ay laging nahahati sa dalawa: isang purong buildApp(deps) na tumatanggap ng mga collaborator bilang argumento (kaya nate-test nang may mga fake, walang totoong network o database), at isang manipis na server.ts na nagkakabit ng mga totoong client (sinadyang walang test). Ang pagkakasunod-sunod dito ay sagrado:

  1. I-validate ang hugis (Zod) — basura, labas agad.
  2. Hanapin ang ad sa cache — hindi sa database. Walang alam na ad? Labas.
  3. Beripikahin ang sig — huwad na pirma? Labas.
  4. Suriin ang r laban sa nakatagong landingUrl — ito ang pinakamahalagang linya ng seguridad sa file na ito, tingnan ang kahon sa ibaba.
  5. Ipadala ang 302. Aalis na ang browser ng user.
  6. Saka pa lang mag-publish, sa loob ng setImmediate — fire-and-forget, para ang mabagal o sirang Kinesis ay hinding-hindi makapagpaantala sa tao.
Ingat! Ang open-redirect na nakatago sa disenyo

Ang sig ay pumipirma lamang sa mga field ng click — hindi kasama ang r. Ibig sabihin, puwedeng kunin ng kahit sino ang isang tunay at may-pirmang click URL at palitan ang r ng kahit anong site — at magre-redirect tayo roon, suot-suot ang ating domain. Iyan ang open redirect, paboritong sangkap ng phishing. Ang lunas: ang r ay dapat eksaktong tumugma sa landingUrl na nakatago sa Postgres para sa ad na iyon — kaya natin ito isinama sa directory contract noong Hakbang 05. Isa itong butas sa orihinal na disenyo sa papel na sinara ng implementasyon sa halip na kopyahin.

07

Fast Lane — dedup, windows, at ang unang consumer

SP3 · Dedup + Aggregation

Ngayon natin bubuuin ang pinakapuso ng sistema: ang consumer na kumukuha ng mga click mula sa stream, nagtatanggal ng duplicate, nagbubuklod sa 1-minutong windows, at nagtutulak ng bilang sa DynamoDB. Dito nakatira ang "exactly once".

Ang pagkakasunod-sunod: windowed-aggregator (purong lohika, walang infra) → mga DynamoDB table → click-dedup → hot-aggregate-store → ang polling loop → ang aggregator service na nagdudugtong sa lahat.

7.1 · @app/windowed-aggregator — purong windowing

Ang mga click ay binibilang kada (ad, minuto) gamit ang event time (ts — kailan pinindot), hindi kung kailan dumating. Ang bawat window ay nananatiling bukas nang dagdag na 2 minuto pagkatapos ng dulo nito — ang watermark — para makahabol ang mga nahuling event. Walang kahit isang import ang package na ito: puro lohika, kaya mabilis at kumpleto ang unit tests nito.

Bakit tatlong hakbang (peek / commit / remove) sa halip na isang "drain"

Ang tuksong API ay isang drainClosedWindows() na nagbabalik at nagbubura nang sabay. Pero isipin ang kabiguan: nakuha mo ang window, sumabog ang DynamoDB sa kalagitnaan ng flush — burado na ang datos, hindi pa naitatala. Nawala ang bilang. Kaya hinati: ang peekClosedWindows ay tumitingin lamang (at nagbabalik pa ng kopya, para walang makagalaw sa loob), at ang commitFlushed ay nagbabawas pagkatapos lamang ng matagumpay na pagsulat, kada ad. Ang bigong ad ay mananatili para sa susunod na pagkakataon.

Kuwento mula sa review: ang double-count na muntik makalusot

May naunang bersyon ng lohikang ito na nag-re-retry ng buong window kapag nabigo ang flush ng isang ad — kaya ang mga ad na matagumpay nang nai-flush ay nadodoble sa muling pagtatangka, at lumalala pa sa bawat retry. Nahuli ito sa code review, at ang ayos — commitFlushed(windowStart, adId, flushedCount) kada ad, pagkatapos lang ng tagumpay ng ad na iyon — ang dahilan kung bakit ganiyan ang hugis ng API ngayon. Sa sistemang pera ang binibilang, ang retry na hindi idempotent ay bug sa invoice.

Walong test ang nagbabantay dito (nasa src/index.test.ts) — kabilang ang: hindi pa sarado ang window bago ang watermark; ang peek ay hindi nagbubura; ang nahuling event sa nabura nang window ay nagbubukas ng sariwang window (na maghihintay ulit ng watermark); at ang binabalik ng peek ay depensibang kopya. Pansinin din kung paano tine-test: ipinapasa ang oras bilang argumento (nowMs) sa halip na i-mock ang orasan — mas simple, mas mabilis, walang mahika.

Bakit dalawang tier — at bakit hindi ito dobleng trabaho

7.4 · @app/hot-aggregate-store — atomic na pagdaragdag

Bakit ADD at hinding-hindi overwrite

Exact Lane — archive, reconciliation, at billing

SP5 · Archive + Billing

Ngayon ang pera. Ang fast lane ay tantiya na mabilis; ang lane na ito ang pinagbabatayan ng invoice: bawat raw event papunta sa S3 bilang Parquet, isang reconciliation query na muling nagko-compute ng eksaktong bilang, at ang statements na binabasa ng billing.

Ang pilosopiya ng lane na ito: gawing nakakabagot ang muling pagproseso

Ang archive ay hindi dinededup — sinadya. Isinusulat ng archiver ang lahat ng makita nito, kasama ang mga retry at duplicate, walang filter. Ang katumpakan ay nakatira sa isang SQL query: COUNT(DISTINCT cid) sa reconciliation time. Kaya ang pag-replay ng parehong data ay laging parehong sagot. May bug? Patakbuhin muli ang query. Nag-update ang fraud model? Patakbuhin muli ang query. Kung pre-filtered ang archive, bawat replay ay nakasandal sa pag-asang tama ang filter noon pa man.

9.2 · @app/parquet-archive — DuckDB bilang lokal na Athena

Sa totoong AWS, ang reconciliation ay Athena query sa ibabaw ng S3. Nang lokal, ang DuckDB ang gaganap: isang SQL engine na nakatira sa loob mismo ng Node process (walang server), marunong magbasa't magsulat ng Parquet nang direkta sa S3. Ang package na ito ang may hawak ng dalawang operasyon ng lane: isulat ang batch at i-reconcile ang isang araw.

  • Maraming maliliit na immutable na file (part-<oras>-<random>.parquet) — dinadagdagan lang, hindi kailanman binabago, kaya walang read-modify-write na sakit ng ulo. Ang read side ay simpleng read_parquet('…/*.parquet').
  • Ang excludedCids ay isang paunang-nakuhang Set, hindi isang isInvalid(cid) na callback kada row — milyun-milyong row ang dadaanan ng query; ang paghihintay sa isang JS callback bawat row ay pagsira sa mismong dahilan kung bakit SQL ito. Nakalagay na ang upuan ng fraud (Hakbang 10) — 'false' muna ang predicate habang walang laman.
  • Ang date validation ang hangganan laban sa injection — ang date ay idinidikit sa S3 path at sa SQL, kaya ang ^\d{4}-\d{2}-\d{2}$ na regex sa bucketPrefixForDate (at muli sa API layer) ay seguridad, hindi kaayusan lang.

  • Nananalo ang previewBot sa velocityFlag. Ang kilalang bot user-agent ay pinakamalapit sa "kumpirmado" na kayang abutin ng rule-based na tseke — invalid agad; ang velocity ay pahiwatig lamang — suspicious.

Ang balangkas ng disenyo ay "ang suspicious ay nakabinbin hanggang ma-review; ibubukod kung hindi naresolba pagsapit ng closing" — pero walang review mechanism ang pipeline na ito, kaya lahat ng suspicious ay "hindi naresolba" sa konstruksyon pa lang. Ang blanket exclusion ang konserbatibong bunga — mas mabuting hindi masingil ang kahina-hinala kaysa masingil ang bot. 10.5 · services/fraud-scorer — ang pang-apat na consumer

Salamat sa shared loop ng Hakbang 07, ang buong serbisyo ay halos pagdudugtong na lamang:

  • Sinadyang HINDI kumukunsulta sa dedup ang scorer. Ang duplicate na paghahatid ng isang mapanlokong click ay ebidensya pa rin tungkol sa cid na iyon, at ang muling paghatol sa parehong input ay idempotent naman — walang poprotektahan ang dedup dito.
  • Ang petsa ng hatol ay "ngayon" sa oras ng paghatol, na tumutugma sa partition date ng archiver para sa sariwang mga click. Kilalang kisame: ang event na sobrang tagal bago dumating (lampas hatinggabi) ay maaaring mahatulan sa ibang petsa kaysa sa kinalagyan ng archive nito — tinatanggap na limitasyon ng rule-based na yugtong ito, nakatala sa mismong komento ng code.

Sa Kinesis, ang parallelism ay ang shards: isang consumer process, isang shard. 12.3 · Ang mga sinadyang puwang

Sinasabi ko ito nang tuwiran dahil malaking pagkakaiba sa isang code review ang "hindi namin ito ginawa, at ito ang dahilan" kaysa sa katahimikan:

  • Manipis ang consumer resilience. Kapag nag-throttle ang Kinesis o nag-expire ang iterator, bumabagsak ang consumer at nagsisimula muli mula sa "ngayon" — nawawala ang mga in-memory window at buffer. Tanggap sa tantiyang lane; para sa exact lane, ang archive + reconciliation ang tagapagligtas. Ito ang numero unong hardening item.
  • Walang durable outbox. Ang na-redirect pero hindi nai-publish na click ay tuluyang nawawala.
  • Walang totoong cron. Ang reconciliation ay function na inilalabas sa manual rerun endpoint; ang scheduling ay usapin ng deployment.
  • Walang IaC, walang deployment. Configuration change lang ang pagturo sa totoong AWS, pero ang productionizing (Terraform/CDK, checkpointing, autoscaling) ay sinadyang labas sa saklaw.
  • Walang load test. Ang p99 <100ms ay hangarin, hindi napatunayan — ang wall-clock assertion sa integration test ay likas na palpakin, kaya pagkakasunod-sunod ng tawag ang tine-test natin (publish pagkatapos ng redirect), hindi ang bilis. Dapat may load test bago ito tawaging production-ready.
  • Magaspang ang fraud. IP-only velocity, header-based na bot detection, walang fingerprinting, walang landing beacon, walang review workflow para sa suspicious.

12.5 · Kung ipagpapatuloy mo ito

Ayon sa ranggo ng aktwal na halaga, hindi ng kislap:

  1. Kinesis checkpointing (isang lease table sa DynamoDB) para hindi na mawala ang posisyon ng consumer sa restart. Ito ang tunay na butas.
  2. Durable outbox para sa publish sa hot path — para tuluyang mapawi ang "na-redirect pero hindi nabilang".
  3. Load test laban sa p99 <100ms na hangarin, tapos gawing scheduled job ang reconciliation.
  4. Review workflow para sa suspicious na hatol, para hindi na blanket exclusion ang patakaran.
  5. Historical windows sa query API (?window=) kapag may humingi na — hindi bago may humingi.
Ang huling aral

Tingnan muli ang huling diff ng Hakbang 10.6: isang linya ang nagdugtong ng buong fraud subsystem sa billing. Hindi iyon suwerte — resulta iyon ng isang desisyon na ginawa isang sub-project bago pa: ang paglalagay ng excludedCids na parameter na tumatanggap ng walang-lamang set. Iyan ang pinakamahalagang kasanayan sa gabay na ito: maghanda ng upuan para sa alam-mong-darating, huwag magtayo ng bahay para sa hindi mo pa kilala. Ang unang klase ng paghahanda ay disiplina; ang pangalawa ay ang pinagmumulan ng mga sistemang hindi na maintindihan ng kahit sino sa alas-tres ng madaling-araw.
